Главные причины раздувания:

1. **Скриншоты.** 91 изображение в контексте; каждое затем переотправлялось на следующих шагах.
2. **Полные проверки.** Smoke-тест всех страниц, `/healthz`, `stats`, PWA installability повторялись после мелких правок.
3. **Переписывание документов.** README, ИНСТРУКЦИЯ, ИСТОРИЯ и копии архива обновлялись почти на каждый шаг.
4. **Версии/архив.** Теги, ZIP, bundle и записи версий делались чаще, чем требовался релиз.
5. **Полные файлы и логи.** Много `bash` с выводом целых файлов вместо точечного `grep`/`read`.
6. **Исправление неверно понятой структуры.** Вместо отдельных пунктов меню сначала сделали «Склад» с вкладками; переделка стоила отдельного дорогого этапа.
7. **Повторные запросы.** «Все временные файлы», «инструкции/архив», «версия» и «проверь» повторялись в нескольких сообщениях.

## 5. Что убрано из рабочего процесса

Добавлены:

- **`AGENTS.md`** — запрет на повторные скриншоты, полный smoke, переписывание документов, версии/ZIP и чтение всей истории без необходимости.
- **`PROJECT_BRIEF.md`** — одна страница с текущим состоянием; её достаточно для новой задачи.
- **`docs/TOKEN_REPORT.md`** — этот отчёт.

Рекомендуемый порядок:

1. Для следующей задачи открыть **новый чат**.
2. Приложить только `PROJECT_BRIEF.md` и новый запрос.
3. Не прикреплять `ИСТОРИЯ.md`, старые скриншоты и логи.
4. Проверять UI скриншотом только если UI менялся.
5. Один финальный smoke-тест на релиз.
6. Версию/ZIP/тег обновлять только на релиз.

> Важно: удалить уже отправленные сообщения из текущей сессии нельзя — они остаются в её журнале и в `ИСТОРИЯ.md`. Реальное «убирание» — это **новая сессия с коротким брифом**, без загрузки старой переписки.

## 6. Ожидаемый эффект

При том же объёме работы:

- новый чат с брифом вместо истории на 240+ млн токенов — меньше контекст на каждом шаге;
- отказ от 80–90% скриншотов — меньше изображений в контексте;
- один smoke вместо 5–7 — меньше вызовов;
- без переписывания документов и версий на каждую мелочь — меньше output-токенов.

Ориентир: **сокращение стоимости на 40–60%** на аналогичной задаче.
Основная экономия — не в цене cache-токенов, а в количестве шагов и output.

| Input, cache hit | $0,003 / 1M | $0,006 / 1M |

Peak: 01:00–04:00 и 06:00–10:00 UTC, Пн–Пт. В сессии 353 вызова пришлись на peak, 314 — на off-peak.
Формула: `input×ставка + cache×ставка + output×ставка`.

Поисковые запросы DeepSeek Search/Fetch в сумму не включены; при 9 поисках и 6 fetch это меньше $0,02.
